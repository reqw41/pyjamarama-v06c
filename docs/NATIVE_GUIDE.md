# Нативный i8080: как писать и проверять подпрограммы (этап 2, docs/PORT_PLAN.md)

Цель: оптимизированный нативный код i8080 по JS-модели (src/model/*.js, сверена с ZX). Поведение — как у модели/ZX; алгоритмы можно упрощать, пока
сверка по ЗНАЧИМОМУ состоянию (память данных, атрибуты, журнал примитивов) нулевая. Образцы стиля — src/vec/wally.asm и src/vec/room.asm.

## Платформа
- **Только i8080** (проверка `sjasmplus --i8080`): нет IX/IY, EXX, EX AF, JR/DJNZ, LDIR, BIT/SET/RES, сдвигов CB, `ld de,(nn)`, `ld bc,(nn)`, `ld (nn),de/bc`, `in/out (c)`.
  `ld hl,(nn)`/`ld (nn),hl`, `ld a,(bc|de)`, `ld (bc|de),a`, `xchg`, `xthl`, `pchl`, `daa`, `rlca/rrca/ral/rar` — есть. Условные jp/call/ret: z nz c nc po pe p m.
  Флаг переноса нужен для 16-бит: `add hl,rp`. Многобайтные операции с памятью через HL/DE/BC и аккумулятор.
- Сборка: `cd src/vec && ~/projects/jetpac-v06c/tools/sjasmplus --nologo --i8080 --sym=../../build/vec/pyjama.sym main.asm` (ошибки — сразу видно). Свой файл `.asm` уже включён в main.asm (заглушки).
  Не правьте `main.asm`, `room.asm`, `wally.asm`, `hw.asm`, `layout.inc` и чужие модули; нужна общая правка — опишите её в отчёте.
- Раскладка (layout.inc): данные ZX 0x8200..0xFC9F лежат по адресу `ZX−0x8100` (0x0100..0x7B9F); карта атрибутов ZX 24×32 — `ATTR`=0x7C00 (адрес клетки = ATTR + Y*32 + X);
  стек 0x7F00..0x7FFF (не рассчитывайте на глубину больше ~40 байт: ISR кладёт ещё 8); код — в плоскости 3 (0xE000+), твой файл идёт после room.asm, ORG не нужен.
- **Метки ZX** — файл `zxsym.inc` (`Имя EQU адрес−0x8100`, 202 метки данных: Wally_X, MilkLevel, Room_ObjSlots, Dart1_Pos, …). Бёрите оттуда. Метки, которых там нет (ячейки внутри блоков
  без метки: `IsArcadeMode+1` = PrevHead, `Wally_HeadTurned+1/+2` = Var_F18A/B), описаны в layout.inc. Свои переменные заводите в КОДЕ своего файла (`db`/`dw` с меткой с префиксом модуля): код живёт в ОЗУ.
- Указатели ВНУТРИ данных (таблицы мебели, описаний, текстов, слова с метками) уже пересчитаны в образе; в переменных времени выполнения указатели на данные ZX (например указатель еды)
  в нативной памяти хранятся тоже сдвинутыми. Указатели на КОД в данных (Test*/Action*/Update_Room*) — нули: свои таблицы переходов стройте в коде.

## Примитивы вывода (заглушки до этапа 3; ABI как у ZX — тогда журналы модели и нативного кода совпадают)
- `bmp16`: A = индекс спрайта 16×16 (XOR), позиция — байты `BitmapX`, `BitmapY` в памяти (слово `ld (BitmapX),hl`: L = X, H = Y). Портит всё, что угодно.
- `beep`: BC, DE, HL — параметры звука как у ZX `Beep_Effect`.
- `tile`: A = тайл, D = строка, E = столбец, C = цвет; сохраняет все регистры; сам пишет атрибут. `tile_flip`, `tile_dbl` — то же. `milk_full`, `milk_row`, `clr_inv`, `clr_fx` — см. room.asm/wally.asm.
- Новые листовые примитивы: добавьте метку-заглушку `RET` в СВОЁМ файле и сообщите имя соответствующего примитива модели (PRIM) в плагине (`prims:{метка:'ИмяПримитиваМодели'}`).
- Столкновение со спрайтом Wally: `Wally_HitTest` (HL = позиция чужого спрайта, L = X, H = Y; B = урон; портит A, DE, B…) — как у ZX; `rnd_a` — случайный байт в A.
- Модель обращается к экрану ZX только как к журналу вывода; пиксели нативный код пока не рисует.

## Проверка: tools/lockn.js (нативный код ПРОТИВ МОДЕЛИ)
`node tools/lockn.js ТИКОВ SEED Имя1,Имя2` — для каждого образца берётся реалистичное состояние из ZX-эталона, модель прогоняется на раскладке ZX, нативный код на раскладке Вектора
(cpu80, примитивы перехватываются по меткам, журнал сверяется), потом сравниваются ВСЯ память данных и атрибуты (кроме указателей на код и служебных ячеек). Метка нативной подпрограммы
должна совпадать с именем в стенде (`Имя` — метка в вашем .asm и ключ в `models`). Входные регистры у нативной подпрограммы могут быть любыми — задайте их в плагине (nregs).
**Плагин вашего модуля**: `tools/lockn_plugins/<модуль>.js` (шаблон `_example.js`; другие файлы не трогать): `models` (обёртки модели над реестром R вашего модуля из src/model),
`setup` (подкрутка состояния для редких веток, регистры), `prims`, `ptrvars`. Целевой результат: 0 расхождений на ≥4 seed и всех комнатах/состояниях, где подпрограмма живёт,
каждая подпрограмма вызвана во всех ветвях (проверьте счётчики; подкручивайте память через `setup`). Негативный тест (внести порчу — стенд краснеет) обязателен хотя бы раз.
Случайные числа: `rnd_a` — стенд подаёт те же значения, что модели (по порядку вызовов), если модель берёт их из `inputs.rands`.
Нативные подпрограммы в игре вызывает диспетчер (пишет основной автор): сохраняйте простой интерфейс — вход через память и регистры (опишите в шапке файла), выход — память.

## Размер и скорость
Бюджет нативного кода в плоскости 3 ограничен (~8 КБ на всю игру, из них ~2,7 КБ уже занято; остальное — в дырах данных): пишите компактно (без лишнего push/pop, общие
вспомогательные подпрограммы, таблицы вместо повторов), но корректность важнее. Сообщите в отчёте размер вашего файла.

## Дополнение (этап 4, фронт): ZX как оракул, размещение кода, плагины без модели
- **Размещение.** Плоскость 3 занята (код кончается ~0xFEF5). Пока игра чёрно-белая, плоскости 1..3 невидимы: новый код фронта кладётся в 0xA000..0xDFFF — первой строкой своего файла `ORG MODSLOT_...`
  (layout.inc: MODSLOT_END=0xA000 конец игры, MODSLOT_ROCKET=0xB000 ракета, MODSLOT_FRONT=0xC000 заставка/меню/музыка). Не выходите за 4 КБ слота. Данные модуля — тоже в слоте (в коде, `db`/`dw`);
  большие таблицы ZX берите из образа данных по меткам zxsym.inc. clear_screen чистит только плоскость 0.
- **Оракул ZX вместо JS-модели.** Для подпрограмм, которых нет в src/model, в плагине: `models:{НативнаяМетка:{zx:'МеткаZX', regs:(zregs)=>zregs}}`. Стенд выполнит подпрограмму ZX на настоящем эмуляторе с памятью и регистрами образца,
  соберёт журнал примитивов (bmp/tile/flip/dbl/snd/milkfull/clr...) и значения `LD A,R` (они подаются нативному `rnd_a`), потом сверит память данных+атрибутов и журнал (`tools/lockn.js`, функция zxOracle).
  Подпрограммы, которые ждут клавишу и т.п., проверяйте кусками (метка внутри ZX-кода — тоже годится как вход, если состояние стека не нужно) либо через кадровый стенд tools/vecshot.js.
- **Пиксели** проверяются tools/gfxcheck.js (ZX-экран ↔ плоскость 0): для новых пиксельных операций (ракета: сдвиг строк экрана, экран заставки) расширьте его своим набором — шаблон там же (раскладка: строка ZX y → L = 223−y, колонка = X>>3).
- Звук: `beep`/`fx_noise` — очередь эффектов на ВИ53 (snd.asm), вызывать как у ZX (BC, DE, HL); блокировок нет.
- Что ещё отличается от ZX: клавиатура — `in_state` (вправо/влево/прыжок) и `vec_kbmat` (матрица Вектора, 1 = нажата, ряды по tools/vecshot.js VKEYS); любая клавиша = `vec_kbmat` не нули или `vj_fire`.
